## 1. 目标与范围

这一节回答两件事：**这个阶段要做出什么**，以及**做到什么程度算过关**。

严格执行你确认过的 **V1.0 十项验收标准（DoD）**。DoD 就是"做完的标准清单"，一条一条对：

| # | 类别 | 验收项 |
|---|---|---|
| C1 | 编译期 | 同一个 path 被两个不同的类标注 → KSP（编译时自动生成代码的工具）**报编译错误、直接打断构建** |
| C2 | 编译期 | `@Route(path = "/main")` 这种直接写字符串的写法（叫"字面量"）→ KSP 发 **Warning**（提醒你改用 RouterContract 常量），构建继续、不中断 |
| C3 | 编译期 | 每个 group 各自生成一个 `GroupLoader_<Group>`；`TRouter.init` 执行完**不会去加载具体的页面类** |
| R1 | 运行时 | 调 `TRouter.navigate(path, bundle)` 能成功打开目标 Activity 或 Fragment（Bundle＝Android 用来装参数的"袋子"） |
| R2 | 运行时 | 跳一个没注册过的路径 → 触发 `onLost` 降级回调（降级＝打不开时的兜底处理），**不崩溃**，返回 `NotFound` |
| R3 | 运行时 | `isDebug = true` 时日志完整打印；`isDebug = false` 时日志安静不打印 |
| T1 | 测试 | 用 ActivityScenario + Espresso（Android 官方的界面测试工具，能模拟真人点击）真实点击来触发跳转，**禁止**在用例里直接调 navigate 做白盒断言（白盒＝绕过界面、直接调代码内部接口） |
| T2 | 测试 | `BaseTRouterTest`：`@Before`（每条用例开跑前）重置路由表、`@After`（每条用例跑完后）释放资源，用例之间互不污染 |
| T3 | 测试 | `testBasicNavigation` / `testLostNavigation` / `testConfigDebugMode` 三条全部通过（全绿） |
| O1 | 可观测 | navigate 的**入口/出口**、GroupLoader 的**加载开始/结束**这 4 个节点都输出 `[TRouter]` 日志（埋点＝在关键位置打一行日志，方便事后排查） |

**V1.0 明确不做**下面这些，留给后面的阶段：

- 拦截器（跳转前统一跑的一段检查逻辑）→ V2.0 阶段做；
- 跨进程那一整套：AIDL（Android 提供的进程间通信方式）、动态代理（运行期自动造一个"假的接口实现"，你把调用交给它，它负责转发）、`@CrossProcess`（标注"这个页面允许被跨进程打开"的注解）→ V4.0 阶段做；
- 动态路由与路由图谱可视化 → V5.0 阶段做。

所以，原先规划的「6 大埋点」里，拦截器开始/结束、跨进程发送/接收这 4 条在 V1.0 还不存在。V1.0 只验收上表 O1 里的这 4 个节点。

**统一治理对照**（整个项目只认一套出入口）：

- 统一入口 = 一切行为都走 `TRouter` 单例（单例＝全局只有一个实例）；
- 统一配置 = `TRouterConfig`；
- 统一结果 = `TRouterResult` 密封类，不含 null（密封类＝"结果只有固定这么几种"的类，编译器会逼你把每种情况都写全）；
- 统一契约 = `RouterContract` 常量，路径都从这里取（KSP 见到直接写字符串就发 Warning）。

## 3. 模块布局与依赖方向（D-1，按你确认：`:app` 保留为主干/测试宿主）

> D-1 是当时"设计决策"的编号（Decision 1）；后面出现的 D-4、D-4b、D-5、D-6 也是同类编号，括号里都写了它们指什么。
>
> 要解决的问题：一个框架拆成几个模块、谁允许依赖谁。拆错了就会出环（A 依赖 B、B 又依赖 A），所以下面把依赖方向写死成单向。

```
TRouterDemo/
├── :trouter-annotation      # 纯 JVM Kotlin 库（用普通 Kotlin 编译，不是 Android 库），零依赖 → com.trouter.annotation
├── :trouter-processor       # 纯 JVM Kotlin 库（KSP 处理器：真正生成代码的那个）        → com.trouter.processor
├── :trouter-core            # Android Library（用 AGP9 内建的 Kotlin 支持）            → com.trouter.core
└── :app                     # 主干/演示/测试宿主（保留 com.demo.trouter，不动命名）
```

依赖方向（严格单向，杜绝环）：

```
annotation (无依赖)
   ▲
   │ 编译期引用 @Route
app ──► core ──► (androidx.fragment)        # 运行时：TRouter、RouterContract、RouteMeta…
app ──► annotation                          # 页面类上写 @Route
app ── ksp(project(":trouter-processor"))   # KSP 处理 :app 内的 @Route，生成物落在 :app
processor ──► annotation + ksp-api          # 处理器自身只依赖注解与 KSP API
```

- `:trouter-annotation` / `:trouter-processor` 用 `org.jetbrains.kotlin.jvm` 插件（AGP 内建的 Kotlin 只管 Android 模块，管不到这种纯 JVM 模块）。
- `:trouter-core` 用 `com.android.library`（AGP 9 内建 Kotlin），**不依赖 annotation**——运行时不需要读注解，路由信息全部来自生成出来的代码，这样隔离得最干净。
- `:trouter-remote` 这个阶段**不创建**。

## 4. 各模块 API 草案（动工时可能微调，类型契约稳定）

"API 草案"＝每个模块对外提供哪些类、哪些方法，先画个草图。真正写的时候细节可能有微调，但类型和签名这份"契约"是稳定的。

### 4.1 `:trouter-annotation`（仅一个文件 `Route.kt`）

```kotlin
@Target(AnnotationTarget.CLASS)
@Retention(AnnotationRetention.SOURCE)   // 路由表由 KSP 生成，无需 RUNTIME 反射
annotation class Route(val path: String, val group: String = Route.DEFAULT_GROUP) {
    companion object { const val DEFAULT_GROUP = "default" }
}
```

> ⚠ 开放项 A1（开放项＝还没定、需要你拍板的问题）：`group` 要不要给个默认值 `"default"`（文档里的表格写作 `@Route(path, group)`，没提默认值）。建议给默认值，演示页更清爽；如果需要强制每次都显式写 group（Fail-Fast 风格，也就是"有错就立刻报出来，别拖着"），那就去掉默认值，并让 KSP 在"分不清该用哪个 group"的场景直接报错。当前按「给默认值」设计。

### 4.2 `:trouter-core` `api` 包

| 类型 | 要点 |
|---|---|
| `RouterContract` | V1.0 的常量：`PATH_MAIN = "/main"`、`PATH_SECOND = "/second"`、`PATH_UNREGISTERED = "/not/exist"`（这条是给"演示降级按钮"专用的，故意不注册）。它把路径集中放在一处，是唯一的契约来源；后续新增的业务路径按里程碑继续往这里沉淀。 |
| `TRouterConfig` | 一个 `data class`（数据类）：`isDebug: Boolean = false`、`logSink: ((String) -> Unit)? = null`、`onLost: ((String) -> Unit)? = null`。`logSink` 用来让测试塞一个"日志收集器"进去；`onLost` 是全局的降级回调。**V1.0 不含 `enableMockInterceptor`**（拦截器属于 V2.0，到那时再扩字段，免得先摆一个用不上的配置）。⚠ 开放项 A2：如果你要求 V1.0 就把这个字段预留出来，请指出。 |
| `TRouterResult` | 密封类，**禁止 null**：`Success(val meta: RouteMeta)` / `NotFound(val path: String)` / `NotInitialized`。调用方用 `when` 把失败的分支一条条写全，漏了编译器不放过。 |
| `RouteMeta` | 稳定的核心数据结构（开闭原则：对扩展开放、对修改关闭）：`data class RouteMeta(path, group, targetClassName, kind)`，其中 `kind: RouteTargetKind { ACTIVITY, FRAGMENT }`。**只存类名的字符串，不存 `Class` 引用** → 这样才做得到"真正用到哪个页面才加载哪个页面"（也就是惰性加载）。 |
| `GroupLoader` / `GroupLoaderRegistry` | `interface GroupLoader { val group: String; fun routeMetas(): List<RouteMeta> }`；`interface GroupLoaderRegistry { fun loaders(): List<GroupLoader> }`。生成出来的代码负责实现这两个接口。 |
| `TRouter` | 单例 object：`init(context, config)`、`install(registry: GroupLoaderRegistry)`、`navigate(path, bundle: Bundle? = null): TRouterResult`；另有 `internal fun resetForTest()`（只在 core 内部可见，给 debug 测试底座用）。 |

`internal` 包（只在本模块内部可见的包）里放三样东西：`RouteTable`（path → meta 的注册表，也就是"哪个路径对应哪个页面"的总表）、日志工具（输出 `[TRouter]` + TraceId 的结构化日志，受 `isDebug` 控制）、`FragmentContainerActivity`（承载 FRAGMENT 目标的容器页，见 D-6）。

**注册机制（D-4，请重点评审）**：`TRouter.init(context, config)` 只做核心初始化（读配置 / 日志开关 / onLost / 建一张空路由表），**完全不碰生成出来的代码**（core 不依赖 app，天然解耦）；而"有哪些路径"这份路由元数据的装配，走 TRouter 单例上**唯一的装配 API** `TRouter.install(registry)`，由生成代码 + 宿主调用一次：

```kotlin
// :app 演示宿主初始化（写在 Application 里；测试时由 BaseTRouterTest.provideRegistry() 注入，见 §9）
TRouter.init(applicationContext, config)
TRouter.install(TRouterGroupRegistry)     // 生成的 object 聚合注册表（object 引用无需括号），包名见 §6
```

> 备选方案 D-4b（不推荐）：让 `init` 内部用 `ServiceLoader`（Java 自带的"自动发现实现类"机制）或约定的类名，自动找到注册表 → 需要跨模块拼类名约定，还会踩 Android 上 ServiceLoader 合并的坑；V1.0 只有一个宿主，这么做没有收益。

### 4.3 `:trouter-processor`（KSP2，`SymbolProcessorProvider` 经 `META-INF/services` 注册）

职责与生成物见 §6/§7。KSP 版本候选 `2.2.10-2.0.2`（与 Kotlin 2.2.10 配套，构建时以 Maven 实际解析出来的版本为准，再回填版本目录）。

（这几个词的意思是：KSP2＝这个"编译时生成代码"工具的第 2 代；`SymbolProcessorProvider`＝KSP 规定的处理器入口；`META-INF/services` 是 Java 规定的"声明扩展实现类"的固定写法。）

## 6. 生成代码与惰性语义（D-5）

KSP 扫描 `:app` 内所有 `@Route`，按 `group` 分组生成（生成的包名 = ksp 参数 `trouter.modulePackage` 的值 + `generated`，V1.0 就是 `com.demo.trouter.generated`）：

| 生成文件 | 内容 | 说明 |
|---|---|---|
| `GroupLoader_<Group>.kt` | `class GroupLoader_<Group> : GroupLoader`，`routeMetas()` 返回该组 `RouteMeta` 列表 | path 已经解析成**字面量**写进去了；`targetClassName` 是**类名字符串**；`kind` 由处理器判定（见下） |
| `TRouterGroupRegistry.kt` | `object TRouterGroupRegistry : GroupLoaderRegistry`，`loaders()` 返回全部 `GroupLoader_xxx()` | 宿主/测试调 `install(...)` 时唯一的引用点 |

**惰性是什么意思**（对齐 C3「init 后不加载具体页面类」）：整条 init/install 链路上**从来不用 `Class.forName`、也从不引用页面类的 `::class`**（`Class.forName`＝按类名把类加载出来；生成代码里只写字符串）。页面类要等 `navigate()` 真正执行时才 `Class.forName` 加载（成功、失败都记日志）。`RouteTargetKind` 由处理器沿着符号的父类型链去判定（命中 `android.app.Activity`/`androidx.activity.ComponentActivity` → ACTIVITY；命中 `androidx.fragment.app.Fragment` → FRAGMENT；两个都不是 → KSP 报 ERROR「@Route 目标必须是 Activity 或 Fragment 子类」）。

**FRAGMENT 目标由谁承载（D-6）**：FRAGMENT 类型的路径由 core 内置的 `FragmentContainerActivity`（FragmentActivity + 代码生成的 container + `Fragment.instantiate(className)`）接住，业务方不用自己写容器页。⚠ 开放项 A3：第一轮 UI 用例建议只演示 Activity 目标（`testBasicNavigation` 跳 `SecondActivity`）；Fragment 目标要不要在 V1.0 加一个演示用例，由你定。

## 7. 编译期校验规则（C1/C2 + Fail-Fast）

Fail-Fast＝"有问题就当场失败、当场报出来"，不要拖到运行时才发现。

| 场景 | 处理 |
|---|---|
| 同一个 path 被 ≥2 个类标注（含跨 group） | KSP 报 **ERROR**，把冲突的两个类和来源文件都列出来，打断构建（C1） |
| path 直接写字符串字面量 | KSP 发 **Warning**：`@Route path 请引用 RouterContract 常量`，仍然照常参与生成（C2） |
| path 引用常量（如 `RouterContract.PATH_SECOND`） | 把常量的**字面值**解析出来，参与冲突检测与生成，不发 Warning |
| path 为空 / 含空白 | ERROR |
| 注解贴的不是类 / 不是 Activity·Fragment 子类 | ERROR |
| 常量引用拿不到值（异常场景，见 R-2） | KSP 发 **Warning** + 这条 path 记为 `__UNRESOLVED_CONSTANT__` + **跳过这条路由的生成**（不注册、不参与运行）+ 处理器日志明确提示「RouterContract 常量无法解析，请检查依赖配置」；被跳过的路由会在生成报告里列出来 |

**常量解析的风险（R-2）**：跨模块的 `const val`（RouterContract 在 core 里，对编译期的 `:app` 来说是一份"编译好的二进制依赖"）能不能被 KSP2 求出值，社区里有历史 issue（[google/ksp#839](https://github.com/google/ksp/issues/839) 是 Java 注解方向的反向场景）。Kotlin 2.2.10 配套的 KSP2（基于 Analysis API）预期能解析编译期常量，但按 Fail-Fast 原则，**实现阶段 Step-2 先做一个探针**：写一个最小的模块，里面写 `@Route(path = RouterContract.PATH_X)` 去编译，打印 `KSValueArgument` 的求值结果。

**探针万一失败，行为也是确定的、可以直接照做的**（没有模糊空间）：KSP 对这条常量引用输出 Warning，把 path 值记为 `__UNRESOLVED_CONSTANT__`，**跳过这条路由的生成**（不注册、不参与运行），并在处理器日志里明确提示「RouterContract 常量无法解析，请检查依赖配置」。这条规则已经固化在上表最后一行，探针过不过都不影响后续步骤继续推进；被跳过的路由会出现在生成报告里，方便定位依赖配置问题。

**多模块的局限说明**：KSP 每次运行只看得到当前这个 Gradle 模块里的注解符号；要做到跨模块（将来各 feature 模块各自产路由）的全局冲突检测，得靠后面的里程碑引入一个"聚合"环节。V1.0 只有单个宿主，不受影响。

## 8. 日志与可观测性（O1 + R3）

4 个埋点的输出模板（统一由 Timber 输出，Tag=`TRouter`；消息以 [节点] 开头，不再重复加前缀。Timber＝一个常用的 Android 日志库；Tag＝日志的分类标签）：

```
[GroupLoader][load][start]        group=default
[GroupLoader][load][end]          group=default routes=1 costMs=…
[navigate][entry] traceId=<id> path=/second bundleKeys=0
[navigate][exit]  traceId=<id> result=Success(meta=/second) costMs=…
[navigate][exit]  traceId=<id> result=NotFound(path=/not/exist) costMs=…   ← 随后触发 config.onLost
```

- `traceId`：每次 `navigate` 生成一个（入口日志带上它，一直贯穿到出口日志）；GroupLoader 属于初始化行为，不带 traceId。
- 输出通道：`config.logSink` 为空 → 走 `android.util.Log`；测试里则注入一个收集器。

**R3 的语义**：`isDebug = false` 时**跳过全部日志调用**（logSink 也不触发 → 测试可以用收集器断言"确实是静默的"）。`onLost` 回调不受 isDebug 控制（兜底行为始终生效）。

## 9. 测试底座的落点（已确认：core 的 debug 变体）

- `:trouter-core/src/debug/kotlin/com/trouter/core/testing/`：`BaseTRouterTest`（抽象 JUnit4 规则类；抽象类＝不能直接用、必须被继承的类；JUnit4 规则类＝JUnit 里给一批用例统一做前置/收尾的写法）、`TestConfig`（继承 `TRouterConfig`，往里注入 logSink 收集器 + onLost 记录器 + `isDebug=true`）。

- `BaseTRouterTest`（抽象类，放在 core 的 debug 源码集里，**不引用任何 :app 的生成类**，否则 core:debug 编译时会因为找不到 `TRouterGroupRegistry` 而失败）：
  - 抽象方法 `abstract fun provideRegistry(): GroupLoaderRegistry` —— 由 `:app` 的 androidTest 子类实现并返回生成物 `TRouterGroupRegistry`（:app 的 KSP 生成 object）；core:debug 只依赖 `GroupLoaderRegistry` 这个接口；
  - `@Before` → `TRouter.resetForTest()` + `TRouter.init(ApplicationProvider 上下文, createConfig())` + `TRouter.install(provideRegistry())` + 清空收集器；`@After` → reset 释放；
  - `createConfig()` 可以被子类覆写（`testConfigDebugMode` 就覆写了 `isDebug`），另外提供 `reInit(config)` 供用例内切换配置。代码骨架见《V1.0-测试方案》§4.2。

- 说明：core 的 debug 测试依赖（junit4、androidx.test:core 等）会经 debug 变体流进 `:app` 的 debug 运行时 —— `:app` 本来就是测试宿主，可以接受，而且不会进 release。

- 具体用例（3 条）的设计见《V1.0-测试方案》§4。
