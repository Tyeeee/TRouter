# TRouter V4.0 跨进程路由 · 测试报告

> **先说人话**
> 这份报告验证的是 V4.0 新做的「跨进程」：页面被要求开在另一个进程里时，宿主进程怎么把"打开这个页面"的请求送过去、再把结果拿回来。
> 主要看四件事：两个真实进程之间通道能不能通、结果（成功/找不到/被拦）能不能原样回传、没标允许跨进程的页面会不会被拒绝、以及老的 20 个用例有没有被改坏。
> 期间还抓到一个严重缺陷：通道连上之后，第二次再发请求永远没人派发，必然超时——已修复并加了自动化回归用例（见 §6 第 0 条）。
> 结论：通过——全量 26 个用例连跑两遍全绿（run27 / run28）。

先认几个报告里反复出现的说法：

- **V1.0 / V2.0 / V3.0 / V4.0……**：本项目的里程碑版本号，每个版本加一层能力（V1 基础跳转、V2 拦截器、V3 多模块、V4 跨进程、V5 动态路由）。

- **A1–A6**：`docs/V4.0-跨进程路由方案.md` 这份方案里的条目编号。
- **AIDL**＝Android 提供的进程间通信方式，本项目内部用它传请求和结果；**Bundle**＝Android 传参数的袋子；**host**＝宿主进程（也就是主 App 进程 `com.demo.trouter`）；**:remote**＝被另开出来的第二个进程 `com.demo.trouter:remote`；**pid**＝系统给每个进程分的编号。

## 6. 测试口径说明（诚实留痕）

0. **严重缺陷的定位与修复（真实复现，最重要的一条）**：
   现象：第一次跨进程点击成功；返回之后再点，**必然 15s 服务超时**（用户实采 logcat：send 23:23:14 → fail 23:23:29，正好是一个超时窗）。
   根因：`RemoteRouter.navigate` 只把请求放进 pending 队列，而唯一的派发点是 `onServiceConnected`；**服务已经连上时（第二次及以后），没有任何触发点去派发新请求** → 请求一直空等到超时。第一次之所以成功，只是碰巧走了 bind→connect 那条派发路径。
   修复：navigate 在 ensureConnecting 之后补一个 `drainIfConnected()`——服务已连接就立刻派发全部待处理请求；冷连接后的派发仍由 onServiceConnected 负责。另外把超时窗从 8s 放宽到 15s，超时后解除 connecting 悬挂状态（此前被误判成"冷启动慢"，真正根因如上）。
   复验：手动「成功→返回→再点」两次都是秒级 Success（logcat #2 的 recv 在 23:24:23.322）；自动化回归 **S12-5** 把这个场景锁死。
   **进一步加固（评审后重写）**：不再依赖"在正确的位置补一次调用"这种顺序论证——RemoteRouter 重写成「单后台线程 trouter-remote + 状态迁移驱动派发」：
   请求入队、连接回调、超时、派发全部在同一个 worker 上串行执行（无锁、不会交错）；入队之后和连接建立之后这两个状态点都会主动 dispatch，所以请求入队后只可能走向「真的执行」或「明确 Blocked」，不存在没人派发的盲区；
   binder 的跨进程调用挪到后台线程，主线程只收 onResult 回调；LogRecorder 改成同步，以支持多线程写日志；服务中途断开时，等待中的请求会明确失败，而不是静默悬挂。
1. S11 UI 用例里，远端页面的**视觉断言**没有放进 Espresso：远端 Activity 在独立进程，Espresso 只挂宿主进程的窗口，没法直接断言另一个进程的视图（跨进程 pressBack 也用不了）。改成：真实点击 + host 侧断言「远端回传 Success 日志」（通道全链路是真跑的），远端页面展示靠手动走查 + 截图佐证。
2. 远端未初始化这类深水分支没有逐一构造（:remote 里 Application 必然会 init）；远端 NotInitialized 映射成 Blocked("remote 未初始化")由 codec 语义保证（编码层已经固化，S12 没有单测这条构造路径——在此留注）。

## 8. 遗留与说明

0. **为什么跨进程通道做成了一个 Service（设计说明）**：AIDL 的标准宿主就是**绑定式 Service**（`bindService` + `ServiceConnection` 回调，也就是「服务创建成功后的回调」），manifest 里要声明组件和 `android:process`。备选方案（ContentProvider 信令 / socket）更 hacky，而且没有标准的生命周期回调；动态代理增强同样需要这个 bind 底座。**单进程用 TRouter 完全不需要它**——只有启用了跨进程的宿主才需要声明 `RemoteRouterService`，core 其余能力零依赖。通道实现成了「单后台线程 + 状态迁移驱动派发」的状态机（见 §6 第 0 条）：服务连接回调只是派发触发点之一，而不是唯一的派发入口。
1. **动态代理**（roadmap 里提过）没有实现：A6 决议把它登记成 backlog 增强项（见 `docs/版本回顾与缺口核查.md` 的 L6 拆分；L 编号就是那份缺口清单里的条目号）。
2. 跨进程通道只承载 Activity 目标（A5）；Fragment 跨进程目标留到以后。
3. remoteService 没配置 / 白名单拒绝 / 超时，这几种情况都用 Blocked 表达（不触发 onLost），S12-1/2 已固化；远端 NotFound 的映射见 S12-3。
4. targetProcess 日志里实际是 ComponentName.flattenToString（方案 §6 示例里的 `:remote` 是概念值，实采见 §5）。
