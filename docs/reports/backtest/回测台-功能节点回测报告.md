# TRouter 功能节点回测报告（回测台）

> **先说人话**：这次不是"再写几个单元测试让它变绿"，而是**在工程里搭了一个回测台**——
> 把每个功能点做成一个**测试节点**，每个节点都**真的去跳转、真的把页面打开、真的跨进程调用**，
> 然后对照"屏幕上究竟发生了什么"给结论。
> 结论：**71 个节点全部通过**；过程中真的挖出了 **3 个库缺陷**（其中 1 个会**让 App 崩溃**），
> 已修复并补了回归节点；另外 1 条是平台行为、8 条是台子自己的坑，都如实记在下面。

时间：2026-09-11　工程：TRouterDemo　设备：模拟器 API 36（arm64）　分支：main

---

## 一、为什么不是"写几个单元测试"

| | 普通单元/API 测试 | 本次回测台 |
|---|---|---|
| 断言对象 | `TRouter.navigate()` 返回了什么 | **屏幕上真的出现了哪个页面**、它真实拿到的 intent/args 是什么 |
| 是否真的开页面 | 多数不真开（或只开一个） | 每个节点都真的开、真的看到、真的关掉 |
| 失败排查 | 看断言 | 每个节点留**证据行**（真实页面类名、真实收到的参数、真实日志行、远端进程的证词） |
| 能否人工复核 | 要看代码 | 回测台本身是**可点的页面**（`/backtest`），一键跑、逐行看结论 |

关键差别在**观测点**：回测台注册了 Activity 生命周期探针，断言写的是
"目标类真的被切到前台了吗""它 intent 里的 path/kind/group 对吗""返回后调用方真的收到数据了吗"，
而不是"navigate 说自己成功了"。很多真实缺陷只有在这个观测点上才看得见（见第四节）。

## 二、回测台长什么样

```
:app/src/main/java/com/demo/trouter/backtest/
├── BacktestContract.kt        回测专用路径常量（沿用"路径只写一次"的规矩）
├── BacktestModel.kt           节点/结果/报告数据模型
├── BacktestRuntime.kt         日志环形缓冲 + Activity 生命周期探针 + 宿主接口
├── BacktestContext.kt         节点执行上下文（真实操作 + 效果断言 + 收尾复位）
├── BacktestStation.kt         节点登记 + 执行器 + 报告落盘
├── BacktestNodesCore.kt       A/B/C 三组节点（基础跳转、参数、返回值）
├── BacktestNodesChain.kt      D/E 两组节点（拦截器、异步拦截器）
├── BacktestNodesDynamic.kt    F/G/H 三组节点（动态路由、别名深链、服务端点）
├── BacktestNodesRemote.kt     I/J 两组节点（跨进程、健壮性）
├── BacktestConsoleActivity.kt 回测台页面（/backtest）：节点清单 + 一键回测 + 逐行结论
├── BacktestFormActivity.kt    操作页（/bt-form）：真实输入框 + 真实按钮发起跳转
└── BacktestRelayActivity.kt   中继页（/bt-relay）：页面里再打开一个页面并回传证据
```

三个页面都是**已注册的真实路由页面**（`@Route` + manifest + 路径常量），
所以"回测台自己"也顺带证明了"任何页面都能被路由打开"（节点 A04/F09 会检查它在路由表里）。

### 节点怎么跑

1. **人工**：主页 → S30「打开回测台」→ 点「开始回测」；每行实时显示 `通过/失败`，失败原因直接摊开；
2. **单个复验**：每个节点右边有「跑」按钮，只跑那一条；
3. **机器**：`BacktestStationTest` 用 Instrumentation 打开回测台、**真的点**「开始回测」，
   等全部跑完，核对"界面上的结论"与"报告里的结论"一致，再要求失败数为 0。

每个节点开始前，台子会把场景复位到同一前置条件（回测台在前台、演示拦截器开关归默认），
跑完只关掉"这个节点自己打开的页面"——**绝不碰别人的页面**（这条规矩是踩坑换来的，见第五节）。

## 四、回测实际挖出来的问题

### 缺陷 1（严重）：等了一下之后才发现目标打不开 → **App 崩溃**

- **节点**：J07（修复前它会把整轮回测直接跑死）
- **触发条件**：链上有**任何"真的会等待"的异步拦截器**（延后放行），并且目标打不开
  （页面类不存在、或漏在 `AndroidManifest.xml` 里声明）。
- **根因**：异步拦截器延后放行后的"剩余链推进"发生在主线程 Handler 回调里，
  而链末端的 `openTarget` 抛出的异常（`ClassNotFoundException` / `ActivityNotFoundException`）
  **没有任何兜底**——异常逃出 Handler 就是未捕获异常。
- **危害**：约定是"打不开就降级成 NotFound + 触发 `onLost` 兜底页"，实际却是**整个 App 崩掉**。
  这不是边缘情况：忘在 manifest 里加一行 `<activity>` 就会命中。
- **修复**：`AsyncRunner` 增加 `failOpen()`，把"链末端打开失败"统一交给 `onOpenFailure` 收口
  （写 Error 出口日志 + 触发 `onLost` + 返回 NotFound）；异步续跑也包进 try/catch。
- **回归**：J07 现在断言"不崩溃 + NotFound + 兜底回调触发 + Error 出口日志"。

### 缺陷 2（中）：同一次打开失败，会因为"链上挂了什么拦截器"而给出两种结果

- **节点**：J02（同步路径）、J08（洋葱包裹路径）
- **表现**：没有（或只有"立即放行"的）拦截器时，打不开的目标 → `NotFound` + `onLost`（正确）；
  一旦链上有**异步拦截器**或**包裹拦截器**，同样的失败变成
  `Blocked(path, "interceptor error: ClassNotFoundException: ...")`——**兜底回调不触发**，
  日志出口也从 `Error` 变成 `Blocked`。
- **根因**：两处 try/catch 把 `member.intercept(chain)` 里抛出的**一切**异常都当成"拦截器自己出错"，
  但 `chain.proceed()` 之后的异常其实来自"打开目标"，跟拦截器无关。
- **危害**：排查时被引向"拦截器写错了"，实际是路由目标的问题；`onLost` 兜底页永远不生效。
- **修复**：区分"拦截器自身抛错"与"放行之后抛错"（`insideProceed` 标记），后者原样上抛，
  由导航层按打开失败收口。
- **踩坑记录**：第一次修复我把复位写在 `finally` 里，结果 `finally` 先于外层 catch 执行，
  标记被清掉，J02/J08 **立刻继续报错**——回测台当场把这个假修复抓了出来。

### 缺陷 3（中）：外部链接的 scheme 区分大小写

- **节点**：G07
- **表现**：`TROUTER://app/second` 被白名单拒掉，返回
  `Blocked(TROUTER://app/second, scheme 未启用（TRouterConfig.deeplinkSchemes 需包含 "TROUTER"）)`。
- **根因**：`navigateUri` 用 `scheme !in deeplinkSchemes` 做**大小写敏感**比较。
- **危害**：URI 的 scheme 按 RFC 3986 天生不区分大小写，Android 的 intent-filter 匹配也不区分；
  从浏览器/短信/扫码进来的链接大小写完全不受 App 控制——表现就是"链接点了没反应"。
- **修复**：白名单按 `equals(ignoreCase = true)` 比较。

### 平台行为（不是缺陷，但会让人误判）：连发跳转时页面会"迟到"

J04（连发 5 次跳转）在负载高的模拟器上出现过"最后一个页面 20 秒后才出现"。
查证结论：**系统会把连发的 Activity 启动排队**（实测某次最后一次启动被推迟约 30 秒），
库这边每次 `navigate` 都立即返回成功、不丢不串。
因此节点的断言落在"页面最终全部出现"并把耗时记为证据，而不是要求"立刻全部出现"。

## 五、台子自己踩的坑（如实记录）

回测台本身也是代码，也会错。这些如果不记下来，下一次就会怀疑"是不是库坏了"：

| # | 坑 | 现象 | 处理 |
|---|---|---|---|
| 1 | 新页面忘了在 manifest 声明 | 三个新页面全部打不开，7 个用例齐刷刷失败 | 补声明；顺带说明这类漏声明正是缺陷 1/2 的触发条件 |
| 2 | `awaitHostBack` 只会"等下一次 resume" | 结果回调先到、回测台**已经**在前台时，它会一直等到超时 | 先看现状再决定要不要等 |
| 3 | 收尾时多关了一个页面 | 把回测台所在的任务关空，之后所有节点都站在错误的前台上 | 只关"本节点打开的页面"，并把"当前在最前的那个"限定在同一集合内 |
| 4 | 用 `REORDER_TO_FRONT` 把回测台提回前台 | **又新建了一个回测台实例**，"宿主"和"屏幕上的那个"不是同一个 | 改用 `CLEAR_TOP + SINGLE_TOP`：复用已有实例并关掉它上面的页面 |
| 5 | 节点里固定睡 300ms 再数页面 | 页面还没切完就数，7/8 反复失败 | 改成轮询等待（`awaitPageCount`） |
| 6 | E06 的改道拦截器不分路径 | 改道后的页面又被改成自己 → 触发防环，节点失败 | 只对目标路径改道（防环本身工作正常，是节点写错了） |
| 7 | 跨进程页面留在屏幕上 | 回测台被压到后台，之后每个节点都站在错误的前台上 | 请远端进程"把自己的页面关掉"（`demoCloseTop`）+ 把回测台提回前台 |
| 8 | 台子只在最后输出结论 | 整轮被外部强杀时，前面跑完的节点白跑 | 改成**每个节点结束就即时输出** |

## 八、已知限制与边界（不想让人误会）

- **跨进程节点会真的起三个进程**（host / `:remote` / `:remote2`），跑完后台子会请远端进程
  "把自己的页面关掉"（等价于用户按返回）——这一步依赖 demo 自己注册的 `demoCloseTop` 端点；
- **远端页面无法被宿主直接 finish**（它在另一个进程），这是 Android 的进程边界，不是库的能力缺口；
- **J04 这类"连发"节点受平台启动队列影响**，负载高时耗时会明显变长（已把观测写进节点证据）；
- 回测台与它的节点属于**演示宿主**（`:app`），不属于库本身；库只提供机制，不认识回测台；
- 本轮数字来自 macOS + AGP 9.3.2 + Gradle 9.5.0 + Kotlin 2.2.10 + JDK 17 + 模拟器 API 36，换环境需重跑；
- 本机模拟器上有其它进程在装/卸包，会把被测进程强杀；被打断的类已重跑，日志保留在 `classes/`。

## 十、库模块命名：保持现状（一次走错路又被撤回来的记录）

**结论：模块目录保持 kebab-case（`trouter-core/`），包名保持 `com.trouter.<模块>`（`com.trouter.core`）。**

中途我曾经把模块目录改成点号形式（`com.trouter.core/`、模块路径 `:com.trouter.core`），理由是"让模块名和包名看起来一致"。
**这是错的**，已全部撤销：

- **目录不是包名**。包名 `com.trouter.core` 在文件系统上对应的是**嵌套目录** `com/trouter/core/`，而不是一个名叫 `com.trouter.core` 的目录；
  把点号当目录名用，任何 Java/Kotlin 工程都不会这么建，IDE 与构建缓存看到的名字也会变得很怪；
- 主流多模块库的写法就是 `trouter-core/` + namespace `com.trouter.core`（目录名与包名本来就是两个层面的东西：
  目录/模块名是构建系统的工程路径，包名是代码的命名空间）；
- 想保留"层级感"的规范替代方案是**嵌套模块**：目录 `trouter/core/`、模块路径 `:trouter:core`——
  但这也只是风格选择，当前工程**没有采用**，保持原样最不容易给使用方添麻烦。

**当前事实（撤销后核对）**：

| 模块目录 / 模块名 | namespace / 包名 | 备注 |
|---|---|---|
| `trouter-annotation` / `:trouter-annotation` | `com.trouter.annotation` | 纯 JVM（无 namespace 配置，包名来自源码目录） |
| `trouter-processor` / `:trouter-processor` | `com.trouter.processor` | 纯 JVM |
| `trouter-core` / `:trouter-core` | `com.trouter.core`（`.api` / `.internal` / `.testing`） | Android Library |
| `trouter-lint` / `:trouter-lint` | `com.trouter.lint` | 可选工具 |
| `trouter-gradle-plugin`（独立构建） | `com.trouter.gradle`；插件 id `com.trouter.route-conflict` | 可选工具 |

> 教训记在这里：**"名字看起来不统一"不等于"要改目录"**。库的对外标识是包名，包名一直是 `com.trouter.*`，
> 没有任何一个模块例外；模块目录名不影响使用方按包名 import。

## 十二、补齐「产出 Intent」的 API（本轮回测台之外的一处能力补全）

**问题（由使用者提出，代码核对确认）**：TRouter 原本**没有任何"产出 Intent"的对外 API** ——
真正造 Intent 的 `openTarget` 是私有的，里面"造 Intent"和"启动页面"写死在一起；
`navigateForResult` 走的是系统 `startActivityForResult`，结果只能从 `onActivityResult` 收。
后果：想用现代 `registerForActivityResult` 的调用方只能绕开 TRouter 自己 `Intent(context, XxxActivity::class.java)`，
于是**丢掉路由解析、别名、拦截器（登录/灰度/兜底）、onLost、页面自述元数据、NotFound/Blocked 语义**。

**顺带发现的文档错误**：`navigateForResult` 的 KDoc 声称"结果由 onActivityResult/**ResultLauncher** 接收" ——
这是错的：`registerForActivityResult` 注册的 launcher 只接收自己发起的请求，根本收不到 `startActivityForResult` 的结果。已改正。

**补上的 API（纯新增，老代码零影响）**：

```kotlin
sealed class TRouterIntent {
    class Ready(val meta: RouteMeta, val intent: Intent) : TRouterIntent()   // 拦截器/别名/重定向都已生效，元数据已写入
    class NotFound(val path: String) : TRouterIntent()
    class Blocked(val path: String, val reason: String) : TRouterIntent()
    data object NotInitialized : TRouterIntent()
}

fun TRouter.buildIntent(path: String, bundle: Bundle? = null): TRouterIntent          // 只解析、只产出，不启动
fun TRouter.buildIntentAsync(path: String, bundle: Bundle? = null, onResult: (TRouterIntent) -> Unit): RouteRequest
```

**实现要点**：内部把链末端拆成 `buildTargetIntent`（只造 Intent，含元数据）+ `openTarget`（按模式收口），
并给整条链加了一路 `captureIntent`（别名/重定向/同步链/异步链/洋葱包裹都透传）。
它走的是**和 navigate 完全同一条链**，因此行为天然一致，不是另起一套。

**验证（回测台节点）**：

| 节点 | 验的是什么 |
|---|---|
| C05 | 用**真的** `registerForActivityResult` 注册 launcher 启动 `buildIntent` 的产物：页面真的打开、结果**只**从 launcher 回调回来（完全不碰 onActivityResult）、Intent 里的 path/kind/group/目标类都对 |
| C06 | 语义与 navigate 一致：未注册 → `NotFound`；门禁拦截 → `Blocked` 且页面不打开；别名 → Intent 指向真实路径 |
| C07 | 链上需要等待时：`buildIntent` 明确拒绝并提示改用 `buildIntentAsync`；`buildIntentAsync` 正常产出；两者都**只产出、不启动** |

**开发过程中自己踩的坑（回测台当场抓到）**：
第一版我只给主要路径透传了 `captureIntent`，漏掉同步链入口那一行（`once(stepChain(members, 0, ...))`），
结果 `buildIntent` 走成"真启动"：页面被打开了、返回 Success、但 holder 为空 → 节点报 `Blocked(未能产出 Intent)`。
三个新节点全红，日志一眼定位。修掉后 71/71 通过 —— 这就是"节点断言落在可见效果上"的价值。
