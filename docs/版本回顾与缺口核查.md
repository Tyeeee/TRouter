# TRouter 版本回顾与缺口核查（V3.0 完成态）

> **先说人话**：这份文档回答两个问题——「V3.0 这个阶段到底该做什么？」「从 V1.0 到 V3.0 的文档和交付里，有没有答应过却没做的事？」
> 它是**结论登记**（每件事最后怎么定的），也是**待办清单**（还没排期的都列在第 4 节）。
> 起因：V3.0 交付之后，你要求把文档回顾一遍。已经能下结论的缺口，本文档和对应的源码注释已经一起改好了。

**先解释会用到的几组编号**（后文直接使用，不再重复解释）：

- `V1.0`～`V5.0`：项目分五个阶段推进，每个阶段叫一个「版本」，数字越大做得越晚。
- `A1/A2…`、`B1/B2…`、`O1/O2…`：各版本方案里「待确认」的条目编号；这些编号下面第 3.1 节会把最终结论补齐。
- `C/R/T` 开头（如 C1、R1、T1）：各版本的验收项编号，保留原编号以便和旧报告对上。
- `L1`～`L11`：待办清单（backlog）里的条目编号，第 4 节逐条列出。
- `×2 绿`：同一批用例连跑两次都通过。
- `KSP`＝编译期自动生成代码的工具；`AIDL`＝Android 提供的进程间通信方式；`白名单`＝允许名单。

**当初你确认过的三条裁决**：§5-A **认可推断出来的定义** → V3.0 的正式定义写在 §2.2；§5-B **登记进待办清单，并在旧文档上加个指路标记**（L1–L4 入册，L1 不单独立项，维持现有的运行时防线）；§5-C **旧方案文档只在开头加指路标记**（已执行，见 V1.0-工程搭建方案 / V1.0-测试方案 文首）。

### 2.2 结论（推断出来的定位，正式登记为 V3.0 的定义）

**V3.0 = 多模块路由聚合（把功能拆成 feature 模块）**：依据就是 §2.1 里唯一那条「后续里程碑要补的功能缺口」锚点（跨模块聚合这一环）。
它和 V1 的单宿主、V2 的拦截器、V4 的跨进程、V5 的动态路由在路线上互不重叠、前后衔接得上，是最符合文档证据的填空。
——**这个定义已经你确认（§5-A），正式登记为 V3.0**；将来要是想起原始规划不一样，按你的回忆再另行修订这里的登记。
