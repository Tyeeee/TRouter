## 1. L4 洋葱/双向链（拦截器模型改造）

- 目标：拦截器不只"放行/拦截/改写"，还能**包裹后续动作**（前置逻辑 → 放行 → 后置逻辑），形成洋葱（请求下钻/响应回卷）。保留 V2 既有语义（Continue/Block/Redirect）不破坏调用方。
- API 要点：
  ```
  interface RouteInterceptor {
      fun intercept(chain: RouterChain): InterceptorDecision
  }
  // chain 暴露：meta/bundle/当前索引/proceed(): 继续执行后续拦截器并最终打开目标
  // 每个拦截器可在 proceed() 前后做前置/后置（洋葱）；仍返回 Block/Redirect 语义
  ```
- 顺序/并发对策（吸取 RemoteRouter 教训）：链的一次执行是**单一调用栈、同步推进**；动态增删只影响"下一次 navigate 的链快照"，绝不并发改写进行中的链 → 每次 navigate 先取**不可变快照**再执行。
- 回归用例（本项专属）：后置观察执行序（proceed 返回后仍执行）、Block 短路时后置不执行、Redirect 与新链语义、两次连续 navigate 无串扰。

## 2. L2 动态增删拦截器

- `TRouter.addInterceptor(interceptor)` / `removeInterceptor(interceptor)`（按实例引用）＋ 查询。
- 线程安全：config.interceptors 变更为**不可变列表快照**（CopyOnWrite 语义：navigate 取快照，增删只在快照切换点生效）。
- 与 L4 关系：注册表独立于"链执行"；注册表修改绝不打断进行中的链。
- 回归用例：导航中增删 → 下一次生效/失效（顺序断言）；并发增删 + 并发 navigate 无崩溃、结果确定。

## 3. L3 @Interceptor（注解级拦截）

- 注解目标：`@Route` 页面声明要附加的拦截器标识；运行时注册表 `标识 → 拦截器实例`。
  ```
  @Interceptor(names = ["login", "audit"])   // 或合并进 @Route 扩展参数（开放项 O-L3）
  @Route(path = ...)
  ```
- 语义：该目标的链 = 全局链 + 该目标注解链（顺序：全局 → 目标附加？开放项 O-L3-顺序）；注册表缺标识 = 编译期/运行期明确失败（不静默）。
- KSP 生成目标拦截器标识清单（沿用 aggregating=true，复用 CrossProcess 生成模式）。
- 回归用例：目标级拦截生效、未注册标识明确失败、非目标路径不受影响。

## 4. F 动态路由热更 / 持久化

- 在 V5 `registerRoute/unregisterRoute` 之上提供：
  - `applyRouteConfig(config)`：**原子批量应用**（一组合法 diff 全成功或全失败；校验 path 合法性/重复，冲突策略与 V5 一致=先移除再注册）；
  - 持久化：当前动态路由集可导出/导入（demo 用应用私有文件；JSON 序列化 RouteMeta 字符串组）。
- 顺序/并发：apply 在单线程串行（复用 remote worker 思路或独立 routeConfig 串行器）；运行中 navigate 取一致快照。
- 回归用例：半途非法条目回滚（原子性）、apply 后 navigate 一致、重复 apply 幂等、导出→导入还原一致。

## 5. L1 跨模块编译期冲突检测

- 现实约束（已论证）：KSP 单次只见本模块，无法在单个 processor 内做跨模块冲突 ERROR。
- 方案（确定性强，不改 KSP 架构）：**构建期校验任务**：宿主/聚合模块注册 Gradle task，在 `kspDebugKotlin`（各模块）之后解析各模块 `generated/GroupLoader_*.kt` 中的 path 常量，**跨模块重复 → 构建失败**（列冲突双方与来源模块）。仍保留运行时 duplicate 告警兜底。
- 回归用例：两个 feature 注入同 path → 构建失败证据；移除后恢复。

## 6. D 动态代理（V4 增强）—— 需要你补语义

- "动态代理"在 V4 roadmap 语境未记录细节，需要你确认语义（开放项 O-D）：
  ① Java/Kotlin 动态代理封装 AIDL binder → host 拿到的 IRouter 是无感代理对象（远程调用透明化，仍走 bound service）；
  ② 还是"代理进程/路由表"式透明分发（调用某 path 自动决定本地 or 远端执行）；
  ③ 其他（你原来的设想）。
- 我倾向 ①（工作量小、与既有通道正交、可作为 backlog 内最自洽解释），② 涉及架构大改需另行评估。
