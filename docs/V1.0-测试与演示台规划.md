## 1. 设计原则（可读性验收标准）

这 6 条原则的验收口径都落在同一个问题上：**一个陌生人能不能看懂？**

| # | 原则 | 验收口径（陌生人能否……） |
|---|---|---|
| P1 | 场景编号制 | 界面上每个可执行场景都有一个稳定编号（S01…），代码/报告/文档三处同号，可以互相查 |
| P2 | 页面自述 | 每个目标页顶部有个横幅，说明：场景号、页面名、路由 path、group、目标类型（Activity/Fragment）、期望结果 |
| P3 | 索引分级 | 主页按「验证类别」分组列场景（比如 导航成功 / 多态目标 / 分组路由 / 降级 / 配置可观测），而不是平铺一堆按钮 |
| P4 | 一键看懂 | 每一行场景都写清「一句话做什么 + 路径 + 期望」，不用读代码就知道点开是在验什么 |
| P5 | 用例对齐 | 每条 Instrumentation 用例都标注它驱动哪个场景号；场景清单页和用例一一对应，没有孤儿按钮、也没有孤儿用例 |
| P6 | 路由目录可查 | 主页带一份「当前已注册路由表」的只读清单（path/group/kind/目标类），用来证明注册是对的、而且是可观测的（具体实现方式见待确认问题 O1） |

（P1–P6 是本文档自己的"设计原则"编号。）

## 2. 场景体系（V1.0 验收域 → 场景）

### 2.1 场景总表

| 场景号 | 验证类别 | 场景名 | 入口操作 | 目标 path / group / kind | 期望结果 | 对应验收 | 对应用例（方法） |
|---|---|---|---|---|---|---|---|
| S01 | 导航成功 · Activity | 基础页面跳转 | 索引点开 S01 | `/second` · default · ACTIVITY | Second 页展示；返回 Success | R1/O1 | testBasicNavigation |
| S02 | 导航成功 · Fragment | Fragment 目标承载 | 索引点开 S02 | `/fragment-demo` · default · FRAGMENT | Fragment 演示页在 core 容器中展示；kind=FRAGMENT | R1(FRAGMENT)/O1（A3 补全） | testFragmentNavigation |
| S03 | 分组路由 | secondary 分组加载 | 索引点开 S03 | `/about` · secondary · ACTIVITY | About 页展示；日志出现 group=secondary 加载起止 | C3/R1/O1 | testSecondaryGroupNavigation |
| S04 | 降级处理 | 未注册路径 | 索引点开 S04 | `/not/exist`（刻意不注册） | 不崩溃；状态栏「未找到路由:/not/exist」；onLost 回调；NotFound 返回 | R2/O1 | testLostNavigation / lostPathReturnsNotFoundAndTriggersOnLost(API) |
| S05 | 配置 · 可观测 | isDebug 日志开关 | 主页说明（用例驱动） | —（由测试注入配置） | debug=true 四节点日志输出；debug=false 静默但导航正常 | R3/T1 | testConfigDebugMode |
| S06 | 导航成功 · 主页自身 | 主页也是注册路由 | 索引点开 S06（或直接启动） | `/main` · default · ACTIVITY | Main 页展示 | R1 | （启动即覆盖，附断言可选） |
| S07 | API 契约（无 UI） | 未初始化 / 幂等 / traceId | 无（测试直接调用） | — | NotInitialized、重复 install 幂等、traceId 贯穿 | 契约分支 | TRouterApiContractTest.* |

> 映射规则：**每个场景号唯一**；界面上能点出来的场景，在 MainRouterTest 里都有对应的 @Test；不经过界面的契约测试归 TRouterApiContractTest；示例用的 ExampleInstrumentedTest 不计入场景体系。
> （S02 那行的"（A3 补全）"：A3 是《V1.0-工程搭建方案》里的待确认问题编号，问的是"Fragment 目标要不要加演示用例"，后来补上了。）
> （"幂等"＝同一个操作重复执行多次，效果和只执行一次一样；"契约分支"＝不点界面、直接验证接口约定的那部分测试。）

## 3. 页面信息架构（改造后）

```
TRouterDemo（App 名 + 副标题：TRouter V1.0 测试台）
├── 场景索引页（MainActivity，@Route /main）
│   ├── 头部：说明一行 + 「路由表快照（只读）」（可选，见 O1）
│   └── 场景分组（每组标题 + 若干行，行=可点击 + 说明文字）：
│       ├── [A] 导航成功——Activity / Fragment / 主页本身 → S01 / S02 / S06
│       ├── [B] 分组路由 → S03
│       ├── [C] 降级处理（未注册路径）→ S04
│       └── [D] 配置与可观测性（isDebug 开关）→ S05（页内说明，由用例驱动）
├── SecondActivity（S01）横幅自述 + 返回
├── FragmentContainerActivity(core) + DemoFragment（S02）横幅自述
├── AboutActivity（S03）横幅自述 + 返回
└── （S05 无独立页：由 MainRouterTest 两阶段驱动并在报告中展示日志）
```

（上面 [A]/[B]/[C]/[D] 是主页上的四个分组标题，分别对应"导航成功""分组路由""降级处理""配置与可观测性"。）

每行场景长什么样（取代"光秃秃一个按钮"）：

```
┌──────────────────────────────────────────────┐
│ S01  基础页面跳转（导航成功 · Activity）          │
│      路径 /second · group default · → 点开       │
│      期望：Second 页展示，navigate 返回 Success   │
└──────────────────────────────────────────────┘
```

实现建议：用纯 View 代码构造每一行（title/subtitle/id=`scenario_s01`…），不引入 RecyclerView/Compose，这样 Espresso 按 id 点击最稳定。
（RecyclerView＝Android 用来滚动展示长列表的控件；Compose＝Android 新的声明式界面写法。这两个都会让"按 id 找元素"变复杂，所以这里不用。）
