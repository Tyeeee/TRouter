# TRouter V3.0 多模块路由聚合方案（评审稿 v0.1）

> 先说人话：这份文档要解决的问题是——所有页面原来都挤在 `:app` 一个模块里，一旦分成多个模块各写各的页面，就没人管「两个模块会不会用了同一个路径」。本方案把页面按功能拆到两个模块，每个模块编译时各自生成自己的「页面清单」，最后由主模块把这些清单汇总装起来。
> 文档里的 V3.0 是项目的功能阶段名（V1.0＝最基础的跳转，V2.0＝拦截器，V3.0＝本次的多模块拆分），只是历史编号。这里的「聚合」＝把各模块各自生成的页面清单汇总到一处。
> 「评审稿 v0.1」＝内部评审用的设计初稿，v0.1 是稿子的版本号。

> 状态：**评审稿 v0.1——已经确认并做完**：§8 列出的五个待定问题（编号 O1–O5）全部采纳了「推荐」那一项。实测证据见 `docs/reports/v3/V3.0-TEST-REPORT.md`（20 个用例连跑两遍，全部通过）。
>
> 做的过程中还发现并修掉了一个原计划没想到的缺陷（报告里留了记录）：编译期代码生成器（processor）生成依赖原来设的是 `aggregating=false`，而 KSP 的增量模式只重新处理「这一轮变了的那几个文件」，于是聚合输出被覆盖成「只含本轮变更的那几个符号」——结果是新增一个 @Route 页面时，GroupLoader 会丢掉其余路由，跨模块冲突检测也跟着失效。改成 `aggregating=true` 后（任何一个 @Route 源文件变化就全量重扫）恢复正常，并用一个「故意写错的负面编译样例」复验过。另外：页面顶部系统栏的工具 `Ui` 上移到 core 的 api 包，供跨模块复用。
> 几个词先解释：「KSP」＝编译期自动生成代码的工具；「增量」＝只重新处理有变化的文件；「aggregating」＝KSP 里的一个标记，表示这个处理器要不要看到全部输入（而不只是本轮变化的输入）；「GroupLoader」＝每个模块生成的「本模块页面清单加载器」；「@Route」＝写在页面类上的注解，用来声明「这个页面归哪个路径管」。

## 1. 要做什么、不做什么（V3.0 验收清单草案）

「验收清单」＝做完之后逐条核对有没有达标的清单。表里的编号 C＝功能项、O＝可观测项、T＝测试项，后文会引用这些编号。

| # | 类别 | 验收项 |
|---|---|---|
| C1 | 结构 | 把路由页面按功能拆到 ≥2 个 feature 模块（类型是 Android Library）里；host（也就是 :app）只留入口页 + 把各模块清单装起来的代码（feature 模块＝装业务功能的模块；host＝装 App 的那个主模块） |
| C2 | 生成 | **每个模块各自跑一次 KSP**：各自生成 `GroupLoader_<Group>` + 本模块的注册表 object（object＝Kotlin 里的单例；包名跟着模块的 namespace 走，namespace＝模块的包名前缀） |
| C3 | 聚合 | host 一次性把所有模块的注册表都装进来；页面类仍然是「用到才加载」——跨模块 navigate（跳转）时只存类名，真正打开那一刻才 `Class.forName`（用字符串类名把类加载进来） |
| C4 | 兼容 | host 自己的 @Route（/main）和各功能模块的路由同时存在、互不影响；同一个模块内部路径重复仍然是编译 ERROR（这条沿用 C1 的验收标准，没变。ERROR＝编译直接报错） |
| C5 | 跨模块防线 | 不同模块之间路径重复（KSP 只看得到自己模块，拦不住这种情况）要在**汇总装配的时候看得出来**：重复注册时打告警日志 + 用契约测试断言路径唯一（并把「先注册的那条生效」这个规则固定下来。契约测试＝把「接口怎么用、返回什么」这个约定用测试固定下来） |
| C6 | 回归 | 原来 18 个用例（S01–S10 这些场景）语义不改、仍然全部通过——测试里只把「去哪儿拿页面清单」从单个注册表换成汇总注册表。（回归＝改完代码后把原来的测试再跑一遍，确认没弄坏旧功能） |
| T1 | 测试 | 跨模块的真实点击（host 主页 → 功能模块里的页面）用界面操作驱动；再补路径唯一性 / 重复告警的契约测试 |
| T2 | 测试 | 原来那套「用例之间互不干扰」的底座继续用；新加的功能模块不能出现孤儿路由（有页面却在场景表里查不到），场景表要一一对应 |
| O1 | 可观测 | 装配时打出的日志按 group（分组标签）覆盖到多个模块；出现重复路径时打出 `[RouteTable][duplicate]` 这样一行结构化日志 |

**V3.0 明确不做的事**：跨模块的「编译期」冲突全局检测（KSP 只看得到自己模块；要让一个编译单元看到全部模块是另一个课题，见 §6 的风险 R-1）；跨进程要用到的 AIDL、动态代理、`@CrossProcess`（放 V4.0 阶段）；动态路由与路由图谱（放 V5.0 阶段）；拦截器和配置的新特性（那属于 V2.0 的范围，已经冻结）。

## 2. 现在的样子，和要补的两个缺口

- 现在：`:app` 一个模块就装着全部 5 个页面（Main/Second/DemoFragment/About/MockSecond），KSP 也只在 :app 跑；core 里的 `RouteTable.register` 对重复路径已经是「不会重复登记」（幂等＝同一个操作做几次，结果都一样；遇到重复会跳过并计数）——但**跨模块的重复会被悄悄吞掉**（没有日志，也没有测试兜着）。
- 缺口 1：工程里没有真实的「多个模块各自生成路由、主模块汇总」的示范；
- 缺口 2：跨模块的路径冲突既看不到，也没有测试把它固定下来。

## 3. 怎么拆模块（O1：建议拆成两个功能模块）

```
:app (host, com.demo.trouter)           MainActivity(@Route /main) + 聚合装配 DemoRouteRegistry + 全部测试
  └─ :feature-demo (com.demo.trouter.feature.demo)
       SecondActivity  S01 /second           (default)
       DemoFragment    S02 /fragment-demo    (default, FRAGMENT kind 跨模块示范)
       MockSecondActivity S09 /mock/second   (mock)
  └─ :feature-about (com.demo.trouter.feature.about)
       AboutActivity   S03 /about            (secondary)
```

- 页面类原封不动搬过去（这些页面都是纯代码，不依赖 xml 布局）；Activity 的注册从 app 的 manifest 搬到各自模块的 manifest（AGP 会自动合并各模块的 manifest，`exported=false` 保持不变。manifest＝Android 的清单文件，用来声明这个 App 有哪些页面和服务）；包名跟着模块的 namespace 改。
- 每个功能模块：用 `com.android.library` + ksp 插件 + `ksp { arg("trouter.modulePackage", "<模块 namespace>") }`；依赖 `annotation` + `core`（运行时不碰生成物，只实现接口）；放 fragment 页的那个模块补上 fragment 依赖。
- RouterContract 仍然放在 core 里共用（所有路径常量只在这一处定义，功能模块的注解直接引用常量）。

## 4. 各模块的页面清单怎么汇总起来（C3/C5）

沿用老规矩：装配只有一个 API `TRouter.install(registry)`，可以多次调用。主模块用**源码里看得见的方式**把各模块显式汇总起来：

```kotlin
// :app 新增（KSP 生成物 + 各模块注册表在这里汇合；GroupLoaderRegistry 只对外暴露 loaders()）
object DemoRouteRegistry : GroupLoaderRegistry {
    override fun loaders(): List<GroupLoader> =
        com.demo.trouter.generated.TRouterGroupRegistry.loaders() +
        com.demo.trouter.feature.demo.generated.TRouterGroupRegistry.loaders() +
        com.demo.trouter.feature.about.generated.TRouterGroupRegistry.loaders()
}
// TRouterDemoApp：init(config) → install(DemoRouteRegistry) —— 一次聚合装配，路径全部登记
```

- 测试这边：`provideRegistry(): GroupLoaderRegistry` 从单个注册表换成 `DemoRouteRegistry`，BaseTRouterTest 和既有用例的断言一行都不用改（用例之间的隔离和轮次计数是按 `loaders().size` 算的，模块变多会自动跟上）。
- 重复路径的防线（C5，也就是 O3 的推荐项）：
  1. `RouteTable.register` 遇到已经存在的 path 时，install 的循环里打出 `[RouteTable][duplicate] path=… keep=<先注册的 targetClassName>`（**把「先注册的那条生效」这个规则固定下来**；重复 install 同一份注册表也会如实提示——它的含义是「这个 path 已经登记过了」，能看见总比悄悄吞掉好）；
  2. 契约测试：汇总之后 `registeredRoutes()` 里没有重复 path、总数符合预期；再注入一个假的 loader（loader＝提供页面清单的东西）制造跨模块重复 → 断言出现 duplicate 日志 + 保留先注册的那条（不崩溃）。
- 「跨模块的编译期拦截」不做（见 R-1），这个取舍在方案里写明。

## 5. 场景和用例

- 场景体系不变（S01–S10）；**S03 与 S01/S02/S09 现在分属不同模块**——在主页上点一下就能跨模块跳转，这件事本身就是 C1/C3 的界面行为证据。
- 新增契约用例（归到 S07/S10 那种风格；是单开新类还是并进现有类，属于 O5 的小问题）：
  - `aggregatedRegistryHasNoDuplicatePaths`：汇总注册之后路径唯一 + 总数符合预期（C5 的契约）；
  - `duplicateAcrossModulesIsLoggedFirstWins`：用假的重复数据 → 出现 duplicate 日志 + 保留先注册的那条 + 不崩溃（C5）；
  - 编译门：往功能模块里塞一个同路径重复 @Route 的反面样例 → 该模块 KSP 报错（这是 C4 的回归证据，验证完就删掉。编译门＝故意写错的样例，用来验证编译器真的会拦住）。
- 全量复跑 = 18 个旧用例 + 新用例；按 T2 的要求隔离跑两遍，全部通过。

## 7. 风险清单

| # | 风险 | 缓解 |
|---|---|---|
| R-1 | 跨模块路径冲突没有编译期拦截（KSP 只有单个模块的视野，要改造成「聚合后的编译单元」动静太大） | 显式汇总（源码里看得见、能审）+ 装配期 duplicate 告警 + 契约测试把唯一性固定下来；文档里写明这个取舍和后续课题 |

| R-4 | 模块变多会让 assemble/install 变慢 | 新增的都只是编译期模块，运行时没有新依赖；复跑脚本继续用 --no-daemon |
