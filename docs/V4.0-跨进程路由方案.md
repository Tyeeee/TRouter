# TRouter V4.0 跨进程路由方案（评审稿 v0.1）

> 先说人话：这份文档要解决的问题是——有些页面必须跑在单独的进程里（进程＝一个 App 里可以拆出的独立运行单元），可跳转请求是在主进程发起的，怎么把它交给另一个进程去打开？本方案用 AIDL（Android 提供的进程间通信方式）在两个进程之间传「要打开哪个路径」，由目标进程里自己的 TRouter 打开页面，再把结果传回来。
> 文档里的 V4.0 是项目的功能阶段名（V1.0 基础跳转 → V2.0 拦截器 → V3.0 多模块拆分 → V4.0 本次的跨进程），只是历史编号。「评审稿 v0.1」＝内部评审用的设计初稿，v0.1 是稿子的版本号。

> 状态：**评审稿 v0.1——已经确认并做完**：§9 列出的六个待定问题（编号 A1–A6）全部采纳了「推荐」那一项。实测证据见 `docs/reports/v4/V4.0-TEST-REPORT.md`（26 个用例连跑两遍全部通过，用的是真实的两个进程）。
>
> 做完后的三点说明（口径以报告为准）：
> - S11 这条 UI 用例对远端页面的**视觉断言**没有放进 Espresso（Espresso＝Android 官方的界面自动化测试框架；视觉断言＝检查页面上到底显示了什么文字/控件）。原因：别的进程里的 Activity 视图，测试代码够不着。改成用「真实点击 + host（主进程）侧的 recv 日志」来断言；远端页面长什么样，由人工走查作为佐证；
> - targetProcess 的日志实际输出的是 `ComponentName.flattenToString()`（§6 示例里写的 `:remote` 只是概念上的值）；
> - 远端返回 NotInitialized 时，会映射成 `Blocked("remote 未初始化")`，这个行为由编解码语义固定下来（编解码＝把数据打包成能跨进程传输的形式，到对面再还原）。

## 1. 先把「跨进程」这个词说清楚（术语与边界）

| 术语 | 定义（本方案） |
|---|---|
| 多进程形态 | **同一个 applicationId 里的多个进程组件**（demo 里内置了一个 `android:process=":remote"` 的第二进程，宿主就是这个演示 app）。不做「跨不同 App」的路由（那要处理签名、权限、白名单，超出 V4 这个演示阶段的价值，明确列为不做。applicationId＝App 的唯一标识） |
| 跨进程导航 | 进程 A（host，主进程）通过 **AIDL 服务**把导航请求发给进程 B（remote，远端进程），**由 B 进程里自己的 TRouter** 解析并打开 B 本地的页面，再把结果摘要返回给 A |
| 结果语义 | B 返回一份「能跨进程传输的结果摘要」→ A 这边重新组装成统一的 `TRouterResult`（Success/NotFound/Blocked/NotInitialized 的语义不变，不会返回 null） |

**V4.0 明确不做的事**：跨 App 的路由、动态代理的实现（属于增强项，见 A6）、动态路由与图谱（V5.0）、跨进程直接承载 Fragment（本版只承载 Activity 目标，Fragment 能不能跨进程留 A5 去定）。

## 2. 要做什么、不做什么（V4.0 验收清单草案）

「验收清单」＝做完之后逐条核对有没有达标的清单。表里的编号 C＝功能项、O＝可观测项、T＝测试项，后文会引用这些编号。

| # | 类别 | 验收项 |
|---|---|---|
| C1 | 通道 | core 提供一条 AIDL 的跨进程导航通道：`bind`（绑定服务）/`navigate(path,bundle)`/结果回传/解绑；同一个进程内跳转仍然走原来的单例路径，**不会有任何回归**（单例＝整个进程里只有一个的对象；回归＝改完代码后再跑一遍原来的测试，确认没弄坏旧功能） |
| C2 | 双进程真实 | demo 里内置第二个进程 `:remote`：用的是同一个 Application 类（但每个进程会各自 init/install 一次），主进程页面可以把 `/second-remote` 这类目标发给 remote 进程执行，并且**真的打开**（用两个进程的 PID 不一样来证明。PID＝进程号） |
| C3 | 统一结果跨进程 | remote 那边返回的 Success/NotFound/Blocked，回到主进程后仍然是统一的密封类 `TRouterResult`（密封类＝一组固定的结果类型，调用方每种都要处理到；`RouteMeta` 里都是字符串，可以完整重建，不会把 Parcelable 这种「只用于传输」的类型漏到业务代码里） |
| C4 | 注册/权限（可选） | 加 `@CrossProcess` 标注 + 编译期校验（只有标注过的路由才允许走跨进程通道）——这一项要不要纳入见 A2 |
| C5 | 埋点 | 新增 `[remote][send]` / `[remote][recv]`（以及失败分支）这几类日志行，日志节点从「6 个」补到「8 个」；受 isDebug 控制（埋点＝在关键位置打日志，方便事后追问题） |
| C6 | 回归 | 原来 20 个用例语义不改、仍然全部通过；跨进程的用例用**真实的两个进程**跑（不拿假实现顶替 AIDL） |
| O1 | 可观测 | 发送/接收的日志里带 traceId（要么和进程内同一次导航关联起来，要么把远端新的 traceId 回显出来。traceId＝一次跳转的唯一编号）；远端返回的结果摘要能看明白 |
| T1 | 测试 | 主进程 → remote 的真实点击/直接调用 + PID 断言；还要覆盖 bind 失败、服务还没就绪时的降级分支（降级＝出问题时退到备用处理方式） |
| T2 | 测试 | 「用例之间互不干扰」的底座继续用；双进程的用例不能影响原来那 20 个单进程用例 |

## 3. 架构的初步设计

```
:app (host 进程，pid A)                        :remote 进程（pid B，同一 application）
  TRouter(navigate path, bundle)                 TRouter 实例（Application.onCreate 在各进程独立执行，
      │                                            自动 init + install DemoRouteRegistry，天然就绪）
      ▼
  core IRouterClient
      │ AIDL bind :remote 的 RouterService        RouterService(远端)
      │ navigateRequest(path, bundle) ──────────► 调 TRouter.navigate(path,bundle)（B 进程本地解析+打开）
      │                                             打开目标：B 进程 Activity（android:process 组件）
      ◄──────────── RouterReply(resultKind, path, meta?, reason?, traceId, costMs)
   重建 TRouterResult 并返回调用方
```

- 代码放哪：本来考虑新增一个 `:trouter-remote` Android Library（那是 core 依赖它，还是它依赖 core？），或者干脆放进 core——见开放项 A1（倾向放在 core 内：新增一个 `internal` 的 AIDL 通道 + 一个 `api` 门面，MVP 阶段不额外开模块；`:app` 用 manifest 声明 `:remote` 进程组件，并跑同一个 TRouterDemoApp。MVP＝最小可用版本；门面＝对外暴露的简单入口）。
- 传输模型：传 `path: String` + `bundle: Bundle`（AIDL 原生就支持），返回自定义的 Parcelable `RouterReply`（里面是 resultKind 枚举 + path + reason + meta 字段字符串 + traceId + costMs）→ core 这边再映射回密封的 TRouterResult（RouteMeta 用字符串重建，纯数据、不引用任何 Class，跨进程天然安全）。
- 生命周期：主进程这边的 `IRouterClient`（通过 bind 把远端的 service 拉起来）用「第一次用到才初始化」，并且可以解绑；远端不可用或超时 → 返回 `Blocked(path, reason="remote 服务不可用")`，或者按映射语义处理（由 A3 定；建议用 Blocked：语义上就是「通道被拦住了」，不触发 onLost）。
- 打开方式：远端执行 navigate 时如果当前没有前台界面 → 用 appContext 加 NEW_TASK 标志来启动（跨进程的 Activity 由系统的任务栈管理；同一个 applicationId 属于同一个 UID，所以即使 `exported=false` 也能显式启动。UID＝系统层面的用户 ID，同一个 App 共用一个）。

## 4. `@CrossProcess` 和编译期校验（对应开放项 A2）

- 如果纳入（建议纳入）：`:trouter-annotation` 新增 `@CrossProcess` 注解（CLASS 级＝作用在类上，SOURCE 级＝只在源码和编译期可见）；编译期处理器新增一条校验：被 @CrossProcess 标注的类必须同时带 @Route，否则编译 ERROR；同时生成 `CrossProcessPaths` 白名单常量表，给 core 的通道校验入参用（进程 B 收到请求时校验：这个 path 没有标注 → 拒绝并回 Blocked。白名单＝允许名单）。
- 如果 A2 选的是「不含」：MVP 就退化成「只要进程 B 注册过这个路径，就能远程导航」（少了一道安全闸，接口不变）。
- 处理器仍然需要 V3 修好的那个聚合设置（`aggregating=true`，V3 阶段已经修好，跨模块沿用同一套规则）。

## 6. 日志（从 4 个节点到 6 个，再到 8 个）

```
[navigate][entry/exit]…（既有）  [interceptor][start/eval/end]…（V2 既有）
[remote][send] traceId=<host> path=/remote-second targetProcess=<ComponentName.flattenToString()>
[remote][recv] traceId=<remote> origin=<host traceId> result=Success(meta=/remote-second) costMs=…
[remote][fail] reason=service 未配置 / 白名单拒绝 / 连接超时 / 调用异常
```

- traceId 怎么关联：主进程发送时带上自己的 traceId；remote 回包时带上 remote 那边的 traceId + origin（来源），两边在日志里可以互相查到（契约用例会断言这一点）。
- 单独一个进程里 isDebug=false 也会关掉 remote 的埋点；跨进程的**行为**不受 isDebug 影响（和拦截器、onLost 是一个级别的）。

## 8. 风险清单

| # | 风险 | 缓解 |
|---|---|---|
| R-1 | AIDL/多进程在 instrumentation 环境里不稳定（bind 有竞态、进程拉起的先后顺序有讲究）。（instrumentation 环境＝跑自动化测试的那个环境，测试代码和 App 跑在一起） | bind 加超时 + 重试窗口；用例里对「服务已就绪」用显式等待（await）；失败分支本身也是验收点 |
| R-2 | 同一个 applicationId 的多个进程共享 Application（每个进程都要 init/install 一次），会重复干活/日志翻倍 | 这是预期内的（每个进程有自己的路由表），日志按 pid 区分；在文档里留下记录 |
| R-3 | Bundle 跨进程的限制（不能放自定义 Parcelable 或非 Bundle 类型） | 契约用例只用系统类型（String/Int/boolean…），方案里把边界写明 |
| R-4 | @CrossProcess 白名单的改动会波及既有的代码生成/测试 | 白名单生成的是独立文件，列表为空时不影响现有行为；`aggregating=true` 已经能防住增量覆盖 |
| R-5 | 动态代理（后续计划里提到过）会让范围膨胀 | 由 A6 定：MVP 不做，只在方案里留一份对比记录（roadmap＝后续计划清单） |
