# TRouter V2.0 拦截器方案（评审稿 v0.1）

> 先说人话：这份文档要解决的问题是——「打开页面前要先做的检查」（登录没登录、灰度没灰度、这个页面临时要不要换掉）原来没地方统一写。本方案把这类检查做成**拦截器**：跳转前按顺序跑一遍，每个拦截器只能说三种话之一——放行、拦下、改道。
> 文档里的 V1.0 / V2.0 是项目的功能阶段名（V1.0＝最基础的跳转，V2.0＝本次要加的拦截器），只是历史编号，不影响怎么用。
> 「拦截器」＝跳转前统一跑的一段检查逻辑；「路径」＝打开页面用的名字，比如 `/second`。

> 状态：**评审稿 v0.1（内部评审用的设计初稿，v0.1 是稿子的版本号）——已经确认并做完**：§10 列出的六个待定问题（编号 A1–A6）全部采纳了「推荐」那一项，代码也已经按这份设计写完。实测证据见 `docs/reports/v2/V2.0-TEST-REPORT.md`（18 个用例连跑两遍，全部通过）。
>
> 做完之后有三处微调（口径以本文档为准）：
> - 拦截日志实际是 start / **每个拦截器打一行 eval** / end 这三组行（§6 的示例已经按这个更新，方便断言「执行顺序」和「提前结束」）；
> - 每跳的 navigate 入口/出口日志都带 `hop=N`（0 表示用户点的那第一次导航），traceId 不变；traceId＝一次跳转的唯一编号，用来把同一次跳转的日志串成一条线；
> - UI 拦截器用例放在单独的类 `TRouterInterceptorUiTest` 里（和 V1.0 的 MainRouterTest 隔开，见 §7）。
>
> 背景：V1.0 方案的 §1 就写明「拦截器留到 V2.0 做」；§4.2 当时留下的话是「拦截器属于 V2.0，到时候再扩字段，避免死配置」——
> 本文档就是这个字段的正式设计。做法上不加 `enableMockInterceptor` 这个布尔开关（布尔＝只能表示开/关两种值的类型），而是用**统一的拦截器列表**来承载（Mock 也走这个列表，见 §4）。
> Mock（模拟）＝用一个假的页面、假的行为来演示效果，不是真功能。

## 1. 要做什么、不做什么（V2.0 验收清单草案）

「验收清单」＝做完之后逐条核对有没有达标的清单。表里的编号 C＝功能项、O＝可观测项、T＝测试项，后文会引用这些编号。

| # | 类别 | 验收项 |
|---|---|---|
| C1 | 配置 | 拦截器统一从 `TRouterConfig.interceptors` 传进去；**列表为空时，行为与 V1.0 完全一样**（回归测试不会有任何差异。「回归」＝改完代码后把原来的测试再跑一遍，确认没弄坏旧功能） |
| C2 | 顺序 | 多个拦截器按列表顺序依次执行；某一个返回 `Continue`（放行）就交给下一个；只要有任何一个返回 `Block`（拦下），立刻停下，**后面的拦截器不再执行** |
| C3 | Blocked 结果 | 返回 `Block` 时，navigate 返回新的密封分支 `TRouterResult.Blocked(path, reason)`（密封类＝一组固定的结果类型，调用方每种都要处理到）：不打开目标页、**不触发 onLost**（onLost＝路径找不到时的兜底回调）、不崩溃；拦截是一次正常行为，**不受 isDebug=false 影响**（这条语义在 §9 的风险 R3 里说明） |
| C4 | Redirect 改写 | `Redirect(targetPath)`（改道：换成另一个路径去打开）会拿新路径重新解析一遍：新路径已注册 → 继续走拦截并打开；新路径没注册 → 返回 `NotFound` 并触发 onLost；累计改道次数超过上限 → 返回 `Blocked(loop)`（loop＝绕圈），防止没完没了地转下去 |
| C5 | Mock 场景 | core（核心运行库）里自带 `MockInterceptor(redirects)`：用一个开关控制，把 `/second` 真实改道到 mock 页（demo 里能点、能测） |
| C6 | 回归 | V1.0 的十个用例语义不改，仍然全部通过；日志节点从 4 个变成 6 个（多了「拦截开始 / 拦截结束」）；出口日志里带上 decision（decision＝这次拦截做出的决定） |
| O1 | 可观测 | 拦截开始/结束这两行输出：拦截器名、是第几个、decision、costMs（costMs＝这一步花了多少毫秒） |
| T1 | 测试 | 用真实界面操作驱动：真的去点主页上 S08/S09 的开关和场景行，再断言结果（不允许直接调 navigate）；直接调 API 验证各个分支的用例归到 S10。（S08/S09/S10＝演示主页上场景行的编号） |
| T2 | 测试 | 继续沿用 BaseTRouterTest 这套「用例之间互不干扰」的测试底座；新增用例不影响原来那十个 |

**V2.0 明确不做的事**：运行中随时加/删拦截器的 API（现在用一个「带状态的拦截器对象」就能满足演示需求，动态增删留到后面的阶段再评估）；页面上用 `@Interceptor` 注解写死的静态拦截；洋葱模型/后置观察模型（也就是「跳转前跑一段、跳转后再跑一段」这种两头包裹的链）——本版拦截器只做放行/拦下/改道三件事，没有请求-响应双向链；跨进程要用到的 AIDL、动态代理（放 V4.0 阶段做。AIDL＝Android 提供的进程间通信方式；动态代理＝运行期自动生成一个「假的接口实现」，把调用转出去）；动态路由与路由图谱（放 V5.0 阶段做）。

**统一口径**：拦截器配置收进 `TRouterConfig`（统一配置）；拦截结果收进 `TRouterResult` 密封类（统一结果，不会有 null）；路径仍然引用 `RouterContract` 里的常量（RouterContract＝集中放路径字符串的地方）；所有行为仍然只走 `TRouter.navigate` 这一个入口。

## 2. 关键设计：什么时候拦、拦下来算什么意思

**拦截点 = 路径解析完之后、目标打开之前**。也就是先拿路径去路径表里查出目标是谁，再拦，最后才真的打开。（在 V1.0 的 navigate 里，就是在 `routeTable.find` 和 `openTarget` 之间插入拦截链。）

```
navigate(path, bundle)
  ├─ 未 init                → NotInitialized
  ├─ find 未命中            → NotFound(path) + onLost        ← 不经过拦截器（丢失 ≠ 拦截）
  └─ find 命中 meta
      ├─ 拦截链（有序，任一非 Continue 短路）
      │    Continue            → 下一个拦截器
      │    Block(reason)       → Blocked(path, reason)，终止
      │    Redirect(target)    → 以 target 重新走完整导航（同 traceId，见 §3）
      └─ 全部 Continue        → openTarget(meta) → Success(opened)
```

上面这张图里的两个词解释一下：「未命中」＝路径表里没查到这条路径；「短路」＝提前结束，后面的拦截器不再跑。

- 为什么选「解析后」而不是「解析前」：拦截器能看到目标页面的**类和分组**（这些信息都在 `RouteMeta` 里），这样 Mock 改写、按目标类做门禁才有依据；没注册的路径保持 V1.0 的「丢失」语义，拦截器不参与，免得把「路径丢失」和「被拦截」混成一件事。
- **门禁示例**：`GateInterceptor` 按 `meta.path == PATH_SECOND` 判断 → 返回 Block。（门禁＝一道「满足条件才放行」的关卡。）**Mock 示例**：`MockInterceptor` 在映射表里命中 → 返回 Redirect。

## 3. 打算加哪些 API（只动 `trouter-core` 的 api 包，annotation/processor 一行都不改）

annotation/processor 分别是「注解模块」和「编译期生成代码的模块」。

```kotlin
// 拦截器：唯一的抽象接口。返回一个决定，不允许返回 null。
fun interface RouteInterceptor {
    fun intercept(meta: RouteMeta, bundle: Bundle?): InterceptorDecision
}

// 三种决定（密封类，不会有 null）：放行 / 拦下 / 改道
sealed class InterceptorDecision {
    data object Continue : InterceptorDecision()
    data class Block(val reason: String) : InterceptorDecision()
    data class Redirect(val targetPath: String) : InterceptorDecision()
}

// core 自带：Mock 拦截器（一张「路径 → mock 路径」的映射表；表里没有的路径一律放行）
class MockInterceptor(
    private val redirects: Map<String, String>,
) : RouteInterceptor {
    var enabled: Boolean = false          // 开关：关掉时全部放行（这是控制行为的开关，不是日志开关）
    override fun intercept(meta: RouteMeta, bundle: Bundle?): InterceptorDecision =
        if (enabled) redirects[meta.path]?.let { InterceptorDecision.Redirect(it) }
            ?: InterceptorDecision.Continue
        else InterceptorDecision.Continue
}

// TRouterConfig：在最后新增一个字段，带默认值 → 原来构造它的代码一行都不用改
open class TRouterConfig(
    val isDebug: Boolean = false,
    val logSink: ((String) -> Unit)? = null,
    val onLost: ((path: String) -> Unit)? = null,
    val interceptors: List<RouteInterceptor> = emptyList(),   // V2.0（本阶段）新增
)

// TRouterResult：新增一个密封子类（编译器会强制调用方补上这个分支，见 §5）
sealed class TRouterResult {
    data class Success(val meta: RouteMeta) : TRouterResult()
    data class NotFound(val path: String) : TRouterResult()
    data object NotInitialized : TRouterResult()
    data class Blocked(val path: String, val reason: String) : TRouterResult()  // V2.0（本阶段）新增
}
```

- 列表里的顺序就是执行顺序；同一个列表里的对象通常由宿主注入「带状态的对象」（比如门禁开关、映射表）。宿主＝用这个框架的那个 App。**开关靠对象自己的状态来控制，不靠动态增删 API**（见 §1 的「不做的事」）。
- `MockInterceptor` 放 core（任何宿主都能复用）；`GateInterceptor` 属于**具体业务形态**，放在 :app 演示层实现，不进 core。
- Redirect 的内部实现：`navigate` 拆出一个私有的 `navigateInternal(path, bundle, traceId, redirectHop)`；**用户一次导航里的 traceId 在所有改道之间保持不变**，每一跳各自记 navigate 的入口/出口日志（跳数累加）；`redirectHop > MAX_REDIRECTS(=3)` → 记为 loop，返回 `Blocked(path, "redirect loop")`。
- Redirect 到一个没注册的路径：按「没查到这个路径」处理（这一跳的出口日志写 `NotFound`，触发 onLost）。

## 4. 配置怎么写、Mock 怎么落地（回答 V1.0 当时在 A2 留的悬念）

V1.0 方案曾写「V2.0 再扩 enableMockInterceptor」——本方案改成**不设单独的布尔开关**，理由是：如果加了这个布尔，它和 `interceptors` 列表在概念上就重复了（这个布尔的本质就是「把内置的 Mock 拦截器挂上去」）。既然要求所有参数都收进 `TRouterConfig`，那就统一走列表：

```kotlin
// :app TRouterDemoApp（演示宿主，isDebug=true）
val mock = MockInterceptor(redirects = mapOf(
    RouterContract.PATH_SECOND to RouterContract.PATH_MOCK_SECOND,   // 新增常量 /mock/second
))
TRouter.init(this, TRouterConfig(
    isDebug = true,
    interceptors = listOf(mock),          // V2.0（本阶段）：演示期挂上 Mock；正式接入的宿主自己决定列表
))
```

- 测试和门禁演示也一样：`TestConfig` 在最后把 `interceptors` 透传下去（见 §7）。
- 新增路径常量 `PATH_MOCK_SECOND = "/mock/second"`，对应新建一个 mock 页（带 @Route，group=mock，只在演示期存在——本仓库本身就是演示宿主，语义上说得通）。

## 6. 日志（从 4 个节点变成 6 个；用 Timber 打，Tag 是 TRouter，只有 isDebug 打开时才打）

Timber＝Android 上常用的日志库。节点＝一次跳转里固定会打出的几类日志行。

新增的三类行如下（每次 navigate 的每一跳，最多打一组；拦截器列表为空时一条日志都不多打，行为与 V1.0 逐字节一致）：

```
[interceptor][start] traceId=65eb7626 path=/second interceptors=2
[interceptor][eval]  traceId=65eb7626 index=1 class=GateInterceptor decision=Continue
[interceptor][eval]  traceId=65eb7626 index=2 class=MockInterceptor decision=Redirect(target=/mock/second)
[interceptor][end]   traceId=65eb7626 decision=Redirect(target=/mock/second) costMs=0
[navigate][exit]     traceId=65eb7626 hop=0 result=Redirect(target=/mock/second) costMs=0
[navigate][entry]    traceId=65eb7626 hop=1 path=/mock/second bundleKeys=0        ← Redirect 后新跳（同 traceId）
[interceptor][start] traceId=65eb7626 path=/mock/second interceptors=2
[interceptor][eval]  traceId=65eb7626 index=1 class=GateInterceptor decision=Continue
[interceptor][eval]  traceId=65eb7626 index=2 class=MockInterceptor decision=Continue
[interceptor][end]   traceId=65eb7626 decision=Continue costMs=0
[navigate][exit]     traceId=65eb7626 hop=1 result=Success(meta=/mock/second, kind=ACTIVITY) costMs=…
```

Block 场景（门禁拦下）：

```
[interceptor][start] traceId=b7ce2f4e path=/second interceptors=2
[interceptor][eval]  traceId=b7ce2f4e index=1 class=GateInterceptor decision=Block(reason=演示门禁开启：拦截 /second)
[interceptor][end]   traceId=b7ce2f4e decision=Block(reason=…) costMs=0
[navigate][exit]     traceId=b7ce2f4e hop=0 result=Blocked(path=/second, reason=演示门禁开启：拦截 /second) costMs=1
```

- 拦截器名：日志里记「第几个 / 类名」（从 `meta` 里拿不到拦截器名，所以记 `interceptors=N` 和 class.simpleName）。
- **R3 这条语义在这里说清楚**：isDebug=false 只关日志；拦截**行为**始终生效（它和 onLost 是一个级别的，属于行为，不是可观测性开关）。
